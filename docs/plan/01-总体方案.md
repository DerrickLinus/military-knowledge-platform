## 1. 背景与定位

公司积累了大量军事条令条例类文档，目前缺少统一的知识管理载体。本项目建设一个**企业级知识库平台**，以开源项目 [WeKnora](https://github.com/Tencent/WeKnora)（腾讯开源，v0.7.2，MIT 许可）为基础进行二次开发，实现知识的入库、检索、问答、沉淀，并向公司其他系统提供知识服务能力。

平台承载三类内容资产（近期以第一类为主）：

| 资产类型 | 说明 | 本期范围 |
|---|---|---|
| 条令条例类文档 | 规章、条令、教程、教材等，文本型与扫描件并存 | **一期核心** |
| 衍生知识资产 | 综述报告、思维导图、FAQ 等由平台生成的沉淀物 | **一期核心** |
| 对抗类时序数据 | 演习/推演类结构化时序数据 | **暂缓**（见 §7.4） |

对抗类时序数据与文档型知识库的数据形态、检索方式差异较大（WeKnora 为文档型 RAG 系统，无时序语义），且目前尚未拿到具体数据样本，因此本期不做设计，仅在演进路线中保留触发条件。

## 2. 三种应用形式

平台最终服务三类调用方。**MVP 阶段只有应用一有真实流量**，应用二、三以"接口契约先行"的方式预留，不为不存在的调用方提前开发代码。

```
┌─────────────────┐  ┌─────────────────┐  ┌─────────────────┐
│ 应用一：员工平台  │  │ 应用二：本体平台  │  │ 应用三：业务Agent │
│ Web UI 逐字使用  │  │ 服务间 API 调用  │  │ 方案阶段，同左    │
└────────┬────────┘  └────────┬────────┘  └────────┬────────┘
         │                    │  (契约已定，代码不开发)  │
         ▼                    ▼                       ▼
   ┌─────────────────────────────────────────────────────┐
   │         WeKnora 知识库平台（本项目交付物）              │
   │   REST API（API Key 能力级授权）· Web UI · 文档管线    │
   └─────────────────────────────────────────────────────┘
```

### 2.1 应用一：员工通用知识平台（MVP 唯一交付形态）

面向公司内部员工的 Web 平台，支持个人使用与协作：

- **快速学习 / 查阅**：对条令条例进行条款级精确问答，引用可回溯原文；
- **知识沉淀**：员工个人文档可入库管理，优质内容可沉淀为部门级/公开级知识；
- **权威来源**：问答必须带引用出处，杜绝无依据生成。

具体功能（智能问答、文档研读、自动综述、思维导图、扫描件支持）见 PRD §3。

### 2.2 应用二：本体平台辅助

公司另一团队在研的"本体平台"业务尚未搭建完成，无法联调。双方约定以 **API 契约**对接：本体平台提出问题 → 传到知识库平台 → 平台完成检索与生成 → 返回带引用的结果。

MVP 交付的是**契约文档而非代码**：WeKnora 自带的开放 API（REST + API Key 能力级授权）即接口层，应用二的对接能力是现成的，不需要额外开发。契约要点：

| 项 | 约定 |
|---|---|
| 认证 | `X-API-Key` 请求头，密钥绑定能力（retrieve / chat / ingest），能力级授权、默认拒绝（fail-closed） |
| 问答调用 | 复用 WeKnora 现有会话问答接口族（支持 SSE 流式），回答携带知识引用 |
| 检索调用 | 复用现有检索接口，可指定知识库范围 |
| 入库调用 | 复用现有文档入库接口（本体平台若需回写语料） |
| 接口清单 | 以仓库 `docs/api/`（23 篇按资源拆分的接口文档）与 Swagger（`/swagger/index.html`）为准 |
| 版本策略 | 本体平台进入联调前，冻结当时 WeKnora 版本并出具正式《接口说明书》附件 |

### 2.3 应用三：其他业务 Agent 辅助

尚在方案阶段。与应用二同等处理：接口契约与上文一致，另可选 **MCP 协议**接入（WeKnora 自带 MCP Server，29 个工具，支持 stdio/SSE/HTTP 三种传输），业务 Agent 框架若原生支持 MCP 可直接挂载，无需自研适配层。同样**契约先行、代码不开发**。

### 2.4 统一 Gateway 的定位

三类应用形式未来可能经一个统一 gateway 路由分发。结论：**MVP 不建设 gateway**。理由：

1. MVP 阶段唯一真实流量是应用一的 Web UI，直连平台即可；
2. 统一认证、审计、限流等职责不属于本期范围（已与 mentor 确认）；
3. WeKnora 自身 API 层已具备认证（JWT/API Key/OIDC）与审计日志能力。

Gateway 进入演进路线（§7.1），触发条件明确，避免为不存在的调用方提前设计。

## 3. 数据与权限分层

### 3.1 分层模型

按 mentor 确认的权限需求，知识资产分三层：

| 层 | 谁可见 | 内容举例 |
|---|---|---|
| **公开层** | 全公司员工 | 通用条令条例、公开教材 |
| **部门层** | 本部门成员（部门可能多级） | 部门内部资料、专业教材 |
| **个人层** | 本人 | 个人笔记、个人文档 |

### 3.2 落地方式：部门 = 租户（MVP 零侵入方案）

WeKnora 的原生隔离单位是**租户（Tenant，即"空间"）**，权限机制为空间内 RBAC（viewer / contributor / admin / owner 四级）+ 资源创建者归属 + 跨租户组织共享（Organization）。映射方案：

```
公开层：建一个覆盖全公司的 Organization，公共知识库共享给该组织
        → 所有部门空间内的成员可见
部门层：每个部门一个空间（租户），部门知识库建在本部门空间内
        → 部门成员加入本部门空间，按 RBAC 角色享有权限
个人层：员工个人空间（默认空间）内自建知识库
        → 仅本人可见，可主动提升为部门级/公开级
```

**MVP 阶段多级部门拍平为一级**（部门 → 员工两层），部门树结构写入演进路线。这一方案的全部实现是"配置 + 管理流程"，不改 WeKnora 源码，代价最小、可随时调整。

### 3.3 明确不做（写入演进路线的项）

| 项 | MVP 替代 | 升级触发条件 |
|---|---|---|
| 文档级权限（同库内不同文档不同人可见） | 权限跟知识库走，需要隔离的内容单独建库 | 出现"必须同库混放但按文档控权"的真实场景 |
| 多级部门树 | 一级部门 | 部门层级管理诉求正式提出且拍平不可用 |
| 密级/分类分级体系 | 文档自定义元数据预留密级字段 | 公司密级管理规范落地 |

## 4. 模型与算力约束

平台部署于私有云，所有模型经公司 dmxapi 网关以 URL + Key 访问，**仅可使用开源模型**。已确认可用：

| 用途 | 模型（dmxapi） | 说明 |
|---|---|---|
| 对话基座 | `qwen3.8-27b` | 问答等高频功能默认模型 |
| 对话备选 | `deepseek-v4-flash-0731` | 速度/成本备选 |
| 高阶任务备选 | `qwen3.8-2.4t-a95b`、`deepseek-v4-pro` | 综述/写作类任务质量不足时升级 |
| Embedding | `qwen3.7-text-embedding` | 向量化 |
| Rerank | `qwen3-rerank` | 重排（dmxapi 清单项，已确认采用） |
| OCR/VLM | `DeepSeek-OCR`、`qwen-vl-ocr-latest`、`qwen3-vl-plus` 等 | 扫描件解析（见技术方案 §6） |
| 翻译（二期） | `qwen-mt-plus / flash / turbo` | 翻译专用系列 |

完整可用模型清单（575 项，已按开源过滤）见 PRD 附录 A。模型经 URL+Key 访问，与公有云 API 在集成方式上无本质区别，能力上限受所选开源模型限制——因此 PRD 对每个功能标注了模型能力依赖等级，质量风险高的功能要求先做模型能力验证（POC）。

## 5. 分期总览

| 期 | 功能 | 交付深度 |
|---|---|---|
| **一期（MVP）** | 智能问答（含教学模式增强）· 文档研读 · 自动综述 · 思维导图 · 扫描件支持 | 本周出 PRD + 技术方案，随后开发 |
| **二期** | 文档翻译 · 辅助写作 · 后训练语料生成 | 本期文档仅做介绍（PRD §4） |
| **三期** | 智慧研讨（异步讨论区）· 学习路径 · 语料审核 | 本期文档仅做介绍（PRD §5） |

分期原则：一期聚焦"文档理解"共享底座（问答、研读、综述、导图同源），翻译/写作技术路径独立放二期，研讨/学习路径依赖前两期行为数据放三期。

## 6. 工程基线

- **基座**：fork 仓库 `DerrickLinus/military-knowledge-platform`，上游为官方 WeKnora（main 分支保持同步）；
- **二开原则**：**跟住上游**——所有扩展走 WeKnora 官方扩展点（Agent 工具注册、内置 Agent/提示词 YAML、RAG 流水线插件、数据库迁移规范），不改动其权限内核，保证可持续合并上游修复与新功能；
- **部署形态**：MVP 为单机 docker-compose（6 个核心容器：frontend / app / docreader / postgres(ParadeDB，自带 BM25+pgvector，无需独立向量库) / redis / sandbox），认证用 WeKnora 本地账号（JWT）；
- **扩展点参考**：`website-docs/06-development/03-extension-points.md`（官方 9 大扩展点文档）。

## 7. 演进路线（本期只定触发条件，不做设计）

### 7.1 统一 Gateway
当应用二或应用三出现**首个真实调用方**时立项。形态定位为薄层：仅认证、路由、审计，业务逻辑一律不进 gateway。

### 7.2 OIDC 单点登录
当公司要求接入统一账号体系时启用。WeKnora 已内置 OIDC 支持（Dex 已有测试配置），属配置级工作。

### 7.3 文档级权限 / 多级部门树
见 §3.3 触发条件。届时改造 Organization 为部门树或将 RBAC 挂接部门，属于对权限内核的手术，需单独立项评估（工作量以月计）。

### 7.4 对抗类时序数据
拿到具体数据样本后立项。初步方向：原始时序数据独立建时序存储与分析服务，**不进 WeKnora 文档管线**；其衍生的分析报告、复盘文档作为普通文档入库；平台 Agent 可通过现有 `database_query` / `data_analysis`（DuckDB）工具对接外部库查询。

### 7.5 k8s 集群化部署
单机 compose 无法满足并发/高可用要求时迁移。WeKnora 自带 Helm Chart（`helm/`），迁移成本可控。

### 7.6 知识图谱（GraphRAG）
条令间的引用、衔接、上下位关系适合图谱化。WeKnora 已内置 Neo4j 图谱管线（可选 profile），可作为二期后的增强方向，与 Wiki 生成能力（WeKnora 已内置）联动形成"条令知识网络"。
